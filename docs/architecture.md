# dARK Internal Architecture

## Scope and principles

dARK is a multi-service identifier and publication platform. An external
repository deposits an object and metadata through the APIs; dARK allocates
an ARK, stores canonical metadata and payloads, confirms IPFS availability,
publishes the immutable record on Besu, and later improves storage durability.
The public ARK lifecycle remains stable while internal processing state is
owned by PostgreSQL and the workers.

## Services

The `apps` group contains the non-validator RPC, Admin API, Store API, Minter
API and its three workers (metadata, replication, chain), Resolver API and
dashboard. Besu validators run in two validator groups; the explorer runs with
validators-a. Storage nodes run Kubo and IPFS Cluster peers. Cluster provides a
global pinset; Store API talks to the local endpoint pool and does not coordinate
replication between sites.

## Minter pipeline

The external flow is reserve → complete metadata → persist → publish → resolve.
Metadata worker persists L1/L2 and stores their CIDs. Replication worker first
confirms one real pin for both levels; only then does the chain worker submit the
record. After Chain publication, durability promotion is maintenance work and
requests the configured target replicas only when the critical pipeline is
clear. Payloads are purged only after both levels meet that target.

`queued`, `pinning`, and `initial_visibility` are normal Cluster progress, not
failures. Availability uses `next_action_at` with bounded backoff. Batch status
calls deduplicate CIDs (up to 200 per request); pages contain up to 100 ARKs.
The worker never holds an ARK lock while making a remote call and revalidates
the row before saving. PostgreSQL advisory locks and row state prevent two
workers from advancing the same ARK concurrently.

## State and consistency

Public states are reserved, draft, update, published and tombstone. Internal
stages are metadata, availability, chain and replication, with pending/ready/
waiting outcomes. A pin is accepted by Store API as soon as Cluster accepts the
CID; publication requires a confirmed pin for L1 and L2. Chain failures remain
recorded as structured errors and are retried only according to the worker
policy; no Recovery Worker is part of the current design.

## IPFS and topology

Each storage node has one Kubo daemon and one Cluster peer. The topology's
`publish_after_replicas` and `target_replicas` define critical availability and
later durability. Peer names are logical; libp2p peer IDs are generated at
runtime. Docker aliases are local-development conveniences, while production
hosts communicate over private/VPN addresses.

## Health and diagnostics

`/health/live` is dependency-free. `/health/read` and `/health/write` are
cheap readiness probes; `/health` is the compatibility aggregate. Worker lite
status reads heartbeats only and always reports metadata, replication and chain.
Full diagnostics are explicit and bounded: they include queues, infrastructure,
wait reasons, batch metrics and error summaries without unbounded ARK scans.

## Chain

Besu uses QBFT with chain ID 2025. RPC is a non-validator in apps; four
validators are split across validators-a and validators-b. Genesis, static
nodes and identities are generated by the internal blockchain runtime and must
not be regenerated for an existing network.

## API boundaries and failure model

The Minter exposes reservation and metadata operations under `/api/v1/arks`;
batch reservation is idempotent when the client item identifier is reused.
Store API accepts payloads at `/v1/store` and reports CID assignments and
replica observations. Resolver exposes public ARK resolution; Admin API owns
authority and operational administration. APIs expose OpenAPI documentation at
`/docs` when enabled.

Transient Store/IPFS states are re-observed at a scheduled next action. Partial
batch failures affect only their CIDs. PostgreSQL transactions and advisory
locks provide ownership; external calls happen outside locks and are checked
again before commit. A restarted worker therefore cannot duplicate publication.

## Configuration ownership

Placement, branches, network addresses and secret references belong to the
inventory. Component `.env` files are generated runtime projections. The
replication policy is declared once as publication and target replica counts;
operational tuning is derived into service environments.
