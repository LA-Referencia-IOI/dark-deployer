# Authorization Alternatives for Minter and Admin API

## Purpose

This document summarizes every authorization model we discussed for
`dark-core-minter-api` and `dark-core-admin-api`, including the options we
considered, the variants inside each option, and the reasons some of them look
better or worse than others.

The goal is to keep the tradeoffs in one place before we commit to a direction.

## Scope and Constraints

These alternatives were discussed under a few practical constraints:

- The current platform is custodial: the backend can act on behalf of an
  authority on-chain because it stores or can recover the authority private key.
- We do not want to expose blockchain concepts directly to normal API clients
  unless there is a strong reason to do so.
- `dark-core-admin-api` is an operator-facing service.
- `dark-core-minter-api` is an authority-facing service.
- We want stronger request authentication than the current development-mode
  header approach.

## Current Baseline

Today the system behaves like this:

- `dark-core-admin-api` registers authorities.
- `dark-core-lib` creates an Ethereum wallet for the authority.
- The authority private key is encrypted and stored on-chain.
- The backend later recovers that private key when it needs to authorize a
  NAAN or publish/update an ARK.
- `dark-core-minter-api` authenticates requests with:
  - mTLS in the stronger path
  - `X-Authority-Id` / `X-Authority-UUID` style identity in local mode

This is the baseline against which the alternatives below were discussed.

## Comparison Matrix

| Option | Summary | Client sees blockchain? | Contract changes? | Keeps backend custody? | Main upside | Main downside |
| --- | --- | --- | --- | --- | --- | --- |
| 0. Current baseline | Keep current custodial model and current auth shape | No | No | Yes | Lowest migration cost | Weakest app-layer auth in local/dev style flows |
| 1. Separate auth key per authority | Authority has a second public/private key just for API auth | No | Maybe | Yes | Strong request signing without changing custody | Two identity planes per authority |
| 2. Ethereum-only auth for every request | Authority signs API requests with its Ethereum key | Partly | Small to medium | Maybe | One identity for API and blockchain | Harder UX, and still ambiguous if custody remains |
| 3. Ethereum-only with direct client tx | Client owns authority wallet and sends chain tx directly | Yes | Medium to large | No | Purest identity model | Explicitly exposes blockchain to client |
| 4. Ethereum-only with relay/meta-tx | Client signs intents, backend relays on-chain | Mostly no | Large | No | Clean non-custodial end state with hidden chain ops | Biggest redesign |
| 5. Ethereum hidden behind SDK/session | Client signs challenge/intents, SDK hides chain details | No at UX level | Medium to large | Usually no | Good UX while keeping strong identity | Requires SDK plus protocol work |
| 6. Custodial plus API credentials | Keep backend custody, add `client_id`/`client_secret` or tokens | No | No | Yes | Simplest practical improvement | Still custodial, adds another secret system |
| 7. Distribute authority private key | Give clients the custodial Ethereum private key | No at API level, but yes in practice | No | Becomes shared custody | Very small implementation effort | Unacceptable security and governance risk |

## Option 0: Current Baseline

### Summary

Keep the current architecture:

- authority wallet generated by the platform
- encrypted authority private key stored on-chain
- backend recovers that key when it needs to act on behalf of the authority
- minter request auth remains based on current mTLS and local identity headers

### Pros

- No contract changes.
- No client migration.
- Already implemented.
- Fully compatible with the current worker and publish flow.

### Cons

- Weak request-level identity in the local/non-mTLS path.
- Trust boundary depends heavily on deployment discipline.
- The backend remains a high-value custodian of authority power.
- It does not improve client-level attribution or revocation.

### Best fit

- Short-term stability.
- Environments where network-level trust is acceptable.

## Option 1: Separate Auth Key Per Authority (SSH-like Model)

### Summary

Each authority would have a second key pair used only for API authentication.
The admin flow would register the public key, and the client would sign requests
with the matching private key.

This was discussed initially using an SSH-like mental model, similar to how
GitHub stores a public key, but the same idea could be implemented with a more
general signing key format.

### Variants discussed

- RSA public key registered by the admin
- A more modern key such as Ed25519 instead of RSA
- Public key stored on-chain or stored in service-managed state

### Pros

- Strong request signing.
- Cleaner than plain identity headers.
- Easy to rotate without necessarily rotating the blockchain wallet.
- Lets one authority have multiple auth clients if modeled correctly.

### Cons

- Introduces a second identity plane:
  - Ethereum wallet for blockchain ownership
  - auth key for API identity
- More concepts to explain and operate.
- Extra storage and key lifecycle design are required.
- If stored on-chain, it adds chain reads or caching needs for every request.

### Best fit

- Teams that want stronger request auth without redesigning the custodial
  blockchain flow.

## Option 2: Ethereum-Only Auth For Every Request

### Summary

Use the authority Ethereum wallet itself as the API identity.
The client signs each sensitive request, and the server recovers the signer
address and compares it with the wallet registered for that authority.

The request would use a signed payload, ideally EIP-712 style, covering fields
such as:

- authority id
- method
- path
- body hash
- timestamp
- nonce

### Pros

- One identity model across API and blockchain.
- No second auth key system.
- Strong proof that the caller controls the authority wallet.

### Cons

- The client now needs signing capability tied to the Ethereum wallet.
- Replay protection becomes mandatory.
- UX becomes harder unless hidden by a helper SDK.
- It is still unclear whether the backend keeps custody or not unless the rest
  of the model is redesigned.

### Best fit

- Teams that want a cleaner long-term identity model and are willing to accept
  request-signing protocol work.

## Option 3: Ethereum-Only With Direct Client Transactions

### Summary

This is the fully non-custodial variant where the client not only signs API
requests, but also signs and sends blockchain transactions directly as the
authority.

### Pros

- Cleanest identity story.
- No backend custody of authority keys.
- The authority wallet is the real source of truth at every layer.

### Cons

- Directly violates the goal of hiding blockchain from the client.
- Requires the client to understand RPC, gas, chain state, and transaction
  lifecycle.
- Breaks the current minter worker model unless redesigned.
- Much larger operational burden for client integrators.

### Best fit

- Power users or wallet-native clients.
- Not a good fit for the product direction discussed here.

## Option 4: Ethereum-Only With Relay or Meta-Transactions

### Summary

The client still uses the Ethereum wallet as its identity, but it never sends
blockchain transactions itself. Instead:

- the client signs an intent
- the backend validates that signature
- the backend relays the operation on-chain
- the contract verifies the authority signature

Typical operations would need relay-friendly variants such as:

- `authorize_naan_by_sig(...)`
- `revoke_naan_by_sig(...)`
- `create_ark_by_sig(...)`
- `update_ark_by_sig(...)`

### Pros

- Preserves a single identity model.
- Keeps blockchain mostly hidden from the client.
- Eliminates backend custody of the authority private key.
- Keeps room for the worker/relay pattern.

### Cons

- Requires smart contract redesign.
- Requires nonce, deadline, replay protection, and signature domain design.
- Requires redesign of `dark-core-lib`, admin API, and minter.
- More moving parts than the current model.

### Best fit

- Long-term strategic end state if we want strong authority identity without
  backend custody.

## Option 5: Ethereum Hidden Behind SDK, Session, and Signed Intents

### Summary

This is the user-experience version of Option 4.

The client should not feel like it is dealing with blockchain directly. So the
API flow becomes:

1. request a challenge
2. sign the challenge with the authority key
3. exchange it for a short-lived session token
4. use the token for regular API calls
5. sign final publish/update intents only when needed

In practice, an SDK or CLI hides the signing details, chain id, nonce shape,
and any crypto formatting from the user.

### Pros

- Strong identity without exposing blockchain concepts to normal users.
- Better UX than signing every raw request manually.
- Compatible with a relay-style backend.
- Good product ergonomics if we want authority self-custody later.

### Cons

- More protocol design than a simple token system.
- Still depends on the larger relay/meta-transaction redesign.
- Requires SDK work and lifecycle support.
- More complex than the simple custodial improvements.

### Best fit

- Medium or long-term product direction if self-custody becomes important but
  the API must stay easy to consume.

## Option 6: Keep Custody, Add API Credentials

### Summary

Keep the current custodial blockchain model unchanged, but stop relying on weak
request identity for the minter. Instead, issue dedicated API credentials per
authority client, for example:

- `client_id`
- `client_secret`
- short-lived bearer token

Under this model:

- `dark-core-admin-api` stays operator-facing
- admin users create, rotate, and revoke authority API credentials
- `dark-core-minter-api` authenticates clients using those credentials
- the backend still uses the custodial authority private key for on-chain work

### Pros

- Smallest useful security improvement.
- No smart contract changes.
- No change to the worker publish model.
- Easy to understand for clients.
- Supports multiple clients per authority.
- Easy to rotate per client without rotating the authority wallet.

### Cons

- Still custodial.
- Adds another secret lifecycle to manage.
- API auth identity remains separate from blockchain identity.
- Backend compromise still has large blast radius because authority power stays
  in the platform.

### Best fit

- The simplest near-term path if we want better API security without large
  architectural changes.

## Option 7: Distribute the Authority Private Key to Clients

### Summary

Under this option, the platform would keep the current custodial model but also
hand the authority Ethereum private key to client applications so they can sign
requests themselves.

### Pros

- Very little implementation work.
- Reuses the existing authority wallet and signing capability.
- Gives strong proof of wallet control at the request layer.

### Cons

- This is effectively shared custody of the authority wallet.
- Anyone with that key can bypass the APIs and act directly on-chain.
- Anyone with that key can spend ETH held by the authority wallet.
- Multiple clients become indistinguishable.
- Per-client revocation becomes nearly impossible.
- Rotation becomes expensive and operationally painful.

### Best fit

- None for this platform. This option was discussed and rejected.

## Cross-Cutting Decision Criteria

When comparing the options above, the main decision axes are:

### 1. Custody

- Do we want the platform to keep acting on behalf of authorities?
- Or do we want authority self-custody over time?

### 2. Client UX

- Can clients handle signing flows?
- Or do we want a normal token-based API with no visible crypto concepts?

### 3. Contract impact

- Are we willing to redesign `Authority.sol` and `dARK.sol`?
- Or do we need to stay compatible with the current contract shape?

### 4. Operational complexity

- How many secrets or keys must be provisioned, rotated, revoked, and audited?

### 5. Identity clarity

- Do we want one identity plane or two?
- Ethereum-only gives one identity plane.
- Separate API credentials or SSH-like auth keys give two.

## Practical Reading Of The Options

If the goal is the smallest near-term improvement:

- Option 6 is the most pragmatic.

If the goal is the cleanest long-term identity model:

- Option 4 plus Option 5 is the strongest end state.

If the goal is to keep the current model and only harden it slightly:

- Option 0 remains viable but limited.

If the goal is strong request signing without redesigning contracts:

- Option 1 is possible, but it creates dual identities.

If the goal is to avoid:

- exposing blockchain to clients
- distributing authority private keys
- and redesigning contracts immediately

then Option 6 is the best short-term fit.

## Options Explicitly Rejected In Discussion

These alternatives were discussed but should be treated as rejected unless the
requirements change materially:

- Option 3: direct blockchain transactions from clients
- Option 7: distributing the authority Ethereum private key to clients

The first conflicts with the product UX constraint. The second creates an
unacceptable security and governance problem.
